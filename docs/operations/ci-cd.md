# CI/CD 方針

## 現在の CI

`ci-repository.yml` は PR と main への push で JSON、workspace 登録、文書のローカルリンクを確認します。
ローカルと同じ `node scripts/verify.mjs` を使用します。
GitHub 上の実行結果、Secrets、Environments、Rulesets は今回確認していません。

## 実装に合わせて追加する検証

| 対象 | 追加する検証 |
| --- | --- |
| Backend | 型チェック、業務テスト、起動、ビルド |
| OpenAPI | 再生成差分、lint、ベース契約との互換性、サンプル検証 |
| iOS | 固定契約からの再生成、Mapper と UseCase のテスト、TestStore、Simulator ビルド |

生成結果には未追跡ファイルも含めて差分を確認します。
アプリの依存と生成ツールを固定し、通常のビルドで Backend の最新契約へ暗黙に追従させません。
古い配布済み iOS との互換性は、生成差分とは別に検証します。

## 公開までの整備順序

1. アプリが実行できるようになったら、それぞれの CI を追加する。
2. 品質チェックの成功と失敗を確認してから必須チェックへ登録する。
3. 検証済み配布物を識別して保存し、ステージングへの自動反映を実装する。
4. 起動と主要機能を確認し、本番反映の判断と復旧手順を整備する。
5. iOS の署名と TestFlight / App Store 配布を別途整備する。

Backend と iOS は独立してリリースします。
本番への認証、デプロイの直列化、監視、DB 変更の互換性は公開先選定後に設計します。
実行する処理のない予約ワークフローは置きません。
