# CI/CD 方針

## ワークフローの責務

| ファイル | 最終的な責務 | 現在の状態 |
| --- | --- | --- |
| `ci-backend.yml` | Backend の静的検証、テスト、ビルド | PR と main push で構成検証のみ |
| `ci-ios.yml` | Swift クライアント再生成、Adapter テスト、iOS ビルド | 手動起動で未実装を示して失敗 |
| `openapi-contract.yml` | 契約再生成、差分、lint、互換性、サンプル検証 | 手動起動で未実装を示して失敗 |
| `deploy.yml` | 検証済み Backend の環境別デプロイ | 手動起動で未実装を示して失敗 |

構成検証の成功は、API の互換性やアプリの品質を保証しません。
GitHub の Secrets、Environments、Rulesets は今回設定していません。
予約ワークフローを必須チェックに登録しません。

## OpenAPI の検証

HTTP スキーマから再生成した契約とコミット済み契約を比較します。
OpenAPI lint、PR のベース契約との破壊的変更検査、サンプルレスポンスのスキーマ検証を実行します。
リリース時には、サポートする公開契約との互換性も確認します。
生成物の変更だけでなく、追加された未追跡ファイルも検出します。

iOS のクライアント再生成は、利用側が採用した契約と固定した生成ツールを入力にします。
初期は同一 PR 内の Backend 契約を使えますが、独立リリースでは公開バージョンへ固定します。
自動再生成の検査を、古い配布済み iOS が動作することの証明とは扱いません。

## Backend と iOS の公開

Backend のデプロイと iOS の TestFlight / App Store 配布は、別のリリースとして扱います。
`deploy.yml` は Backend 用の予約位置です。
iOS の署名、配布証明書、配布先、公開手順は別途設計します。

Backend は CI 成功後に配布物を保存し、ステージングで確認してから本番へ反映する方針です。
同じ配布物を識別して再利用できるようにします。
本番反映の判断方法、クラウド認証、デプロイの直列化、監視、復旧方法は公開先選定後に実装します。
DB マイグレーションの互換性と復旧は、アプリのロールバックとは別に設計します。

## 整備順序

1. ランタイム、生成ツール、テストツール、公開先を決める。
2. 最小の Backend と iOS をそれぞれビルドできるようにする。
3. OpenAPI 生成とクライアント生成を実装する。
4. 各予約ワークフローを実際の検証へ置き換える。
5. チェックの成功と意図的な失敗を確認してから、main の保護を設定する。
6. ステージングの自動デプロイと動作確認を通す。
7. 本番反映と復旧、iOS 配布の手順を整備する。
