# 構成の見直し候補

2026-09-05 の構成確認で見つかった論点です。
機能を束ねる中間ディレクトリの除去は反映済みです。
以下は追加の設計判断が必要な候補であり、現在の配置を変更する決定ではありません。

## HTTP の機能別配置

現在は HTTP のルート、スキーマ、Presenter を `src/interfaces/http/` に集約しています。
機能の変更が `src/<feature>/` と HTTP の共通配置に分散するため、機能単位で完結させる方針とは一致しきっていません。
機能固有の HTTP 処理を `src/<feature>/presentation/http/` に置き、ルート登録と共通エラー変換だけを全体側に残す案を推奨します。
HTTP スキーマからの OpenAPI 生成は、それぞれの機能の公開登録処理を集約すれば維持できます。

## iOS の Mapper の所有者

現在の案では `Core/API/Mappers/` が各機能の内部モデルを参照します。
この構成では機能が増えるたびに Core が機能の知識を持つため、依存方向を再検討する必要があります。
生成クライアントと通信基盤を Core に残し、機能固有の Adapter と Mapper は `Himatch/<Feature>/Infrastructure/` に配置する案があります。
採用する場合、生成型の利用範囲を「Core/API 内だけ」から「通信基盤と機能の API Adapter 内だけ」へ変更します。
いずれの場合も、Domain、UseCase、ViewModel、View へ生成 DTO を流さない境界は維持します。

## 空ファイルと予約ワークフロー

現在の OpenAPI、Xcode プロジェクト、生成設定は予約位置です。
手動起動の予約ワークフローは常に失敗するため、まだ実行価値がありません。
添付との対応確認には役立ちますが、通常の開発では配置を文書に残し、実装時に有効なファイルを追加する方が分かりやすくなります。
同様に、空の層を全機能へ先に作る運用も、使っていない層の維持を強制しない形へ変更できます。

## 構成検証の適用範囲

`make verify`、`scripts/verify.sh`、`pnpm verify` は同じ構成検証への入口です。
開発者向けの正式な入口を一つ決め、他は CI や内部処理で必要な場合だけ残すと保守対象を減らせます。
現在の Backend の `verify` もリポジトリ全体を検証するため、将来は Backend 自身の型チェックとテストへ置き換えます。
`private` と `exports` の検証だけでは、相対パスによる他アプリ実装の import を防げません。
実装開始時には、依存境界を検査する lint またはアーキテクチャ検証を追加します。

## 通知の業務と接続基盤

`src/notifications/` と `src/infrastructure/notifications/` は名前が似ていますが、責務が異なります。
前者は通知の業務規則、後者は送信プロバイダーへの接続です。
冗長さを理由に統合せず、プロバイダー選定後に接続先を表す名前へ具体化することを検討します。
