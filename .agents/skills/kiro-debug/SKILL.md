# kiro-debug

エラー出力、実行コマンド、環境・依存版、対象仕様、作業開始点と変更差分を読む。既に試した操作と結果も受け取り、同じ失敗を繰り返さない。

同期の初期確認には `kiro-spec-sync --check`（読み取り専用）を使い、変更権限がある場合だけ同期を実行する。`spec.json.freshness` が欠落している既存仕様は `unchecked` として対象範囲を調べ、欠落だけで承認を消去しない。`current` は文書整合のみを表し、承認・実装完了の代わりにならない。完了対象に `pending` が残る場合は影響を解決し、本文の意味も照合する。

## 調査

1. 元の症状、再現条件、失敗位置を特定する。関連ログと現行コード・設定を調べ、仮説と確認済みの事実を分ける。
2. 仮説を区別できる最小の確認を実施する。仕様や依存の挙動が不確かな場合は対象バージョンの公式資料で確認する。根拠なく複数の修正を同時投入しない。
3. 原因が実装、設定・依存、実行環境、タスク順序・分割、仕様の矛盾、外部条件のどれにあるか分類する。所有する feature / shared / upstream の箇所で修正する。
4. 古い要件・設計・タスクが原因なら [kiro-spec-sync](../kiro-spec-sync/SKILL.md) で変更根拠、本文、影響先、承認を扱う。コードの不具合はコードで直し、仕様を後付けで弱めない。
5. 最小の修正案と、元の症状の解消・関連回帰を確かめる方法を示す。新しい証拠がないまま同じ再試行を続けない。

## 次の行動

- `RETRY_TASK`: 承認済み範囲内のコード・設定・依存修正、通常のタスク順序や粒度の調整、追加調査で進められる。未解明の場合は次の識別実験を示す。
- `BLOCK_TASK`: 外部サービス、資格情報、ハードウェア、未承認の重要判断を待つが、独立したタスクを進められる。
- `STOP_FOR_HUMAN`: 継続全体が外部条件または人間の製品・要件・範囲判断に依存する。

通常のリポジトリ修正や再試行回数だけを理由に停止しない。承認が必要なら、判断対象、具体的な修正案、依存しない先行作業を示す。

## 報告

spec.json の言語で返す。

```md
## Debug Report
- ROOT_CAUSE: 確認済みの原因、または未確定の仮説と不足する証拠
- CATEGORY: 原因の分類
- OWNERSHIP: 原因を所有する箇所・仕様
- FIX_PLAN: 根拠に対応する修正または次の識別実験
- VERIFICATION: 元の症状と関連回帰の検証方法
- NEXT_ACTION: RETRY_TASK | BLOCK_TASK | STOP_FOR_HUMAN
- CONFIDENCE: HIGH | MEDIUM | LOW
- NOTES: 試行結果、仕様同期や承認の要否
```
