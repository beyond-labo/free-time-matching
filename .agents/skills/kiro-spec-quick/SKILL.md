# 仕様生成の連続実行

`$ARGUMENTS` の feature 名または説明を対象に、初期化・要件・設計・タスクを必要な段階から実行する。`--auto` は今回の範囲の各工程を品質確認付きで自動承認し、生成を最後まで進める指定である。実装の許可は含まない。

1. [kiro-spec-sync](../kiro-spec-sync/SKILL.md) を読み、既存仕様と今回の更新範囲を確認する。同じ仕様の再実行で `-2` などの別仕様を作らない。
2. [kiro-spec-init](../kiro-spec-init/SKILL.md) を実行する。既存仕様なら初期化を省略し、既存メタデータを保持する。初期化ロジックをここで複製しない。
3. [kiro-spec-requirements](../kiro-spec-requirements/SKILL.md) を実行する。内容と根拠が有効な既存工程は再生成せず、変更の影響を受けた最も上流の工程から再開する。
4. 要件承認後、[kiro-spec-design](../kiro-spec-design/SKILL.md) を実行する。`--auto` 時は `-y` を渡す。対話モードでは具体的な要件を提示し、まだ承認されていなければ承認を待つ。
5. 設計承認後、[kiro-spec-tasks](../kiro-spec-tasks/SKILL.md) を実行する。`--auto` 時は `-y` を渡す。対話モードでは設計承認を確認し、生成したタスクは別途承認を待つ。対話モードに黙って `-y` を渡さない。
6. 保存された成果物と spec.json を照合し、同期漏れと失効した承認が残っていないか確認する。タスク生成で実施した統合ゲートの結果を利用し、同じ対象を必須の別 sanity review で繰り返さない。最後のレビュー後に変更があれば影響箇所を再確認する。

各工程の定型的な「次のコマンド」案内は単独実行向けであり、許可された連続実行を止める理由にはしない。`--auto` でも未許可の製品判断、入力不足、品質を確定できない失敗は該当工程で保留し、具体的な再開条件を示す。通常の整合修正は sync に従って継続する。

結果は生成・更新したファイル、品質結果、承認状態、残る判断を示す。品質と承認が揃っていない場合は実装準備完了と表現しない。

各工程の最終反映では sync で現存文書の整合を確認し、`freshness.status` と未同期の `pending` を更新する。`current` は文書整合の状態であり、承認や実装 GO を意味しない。旧仕様に freshness がなくても一律に承認を消去せず、今回の対象から確認する。

## 文書形式

生成と更新には [OKF の共通手順](../kiro-spec-sync/references/okf-workflow.md) を使う。本文のIDと構造を保ち、工程終了時に対象文書と影響先を検査する。初期化だけの場合は未確認状態を維持し、未実施の意味検査を記録しない。
