# 設計レビュー

対象の要件、設計、`spec.json` と関連する steering を読む。
[rules/design-review.md](rules/design-review.md) で品質を確認し、[kiro-spec-sync](../kiro-spec-sync/SKILL.md) の `--check` で古い契約や参照の混在を調べる。

- 実在する既存パターン、型、責務境界、要件の網羅、外部契約と設計を照合する。
- 独立した大きな調査は分担できる。単なるファイル読込は分担しない。
- 指摘は根拠と影響のあるものに絞る。要約は主要な問題に集中させるが、見つけたブロッカーを件数上限で省略しない。
- 結果を左右する未決事項だけを質問する。日常的な設計判断について対話を強制しない。
- レビュー依頼だけなら文書と承認を変更しない。修正も依頼された場合は sync で本文と影響する状態を更新する。

`GO` は設計の品質判定であり、人間の承認や実装成功を意味しない。
未同期や要件との未解決の矛盾がある場合は `NO-GO` とし、対象と修正内容を示す。
未生成の設計を推測して合格にしない。

## 構造と確認対象の検査

[OKF の共通手順](../kiro-spec-sync/references/okf-workflow.md) の `check` を対象範囲へ実行する。機械検査の成功と意味の検査を区別し、古いハッシュや承認を現在の状態の証拠にしない。読取専用の依頼では snapshot、index、状態更新を実行しない。
