# kiro-impl

同期の初期確認には `kiro-spec-sync --check`（読み取り専用）を使い、変更権限がある場合だけ同期を実行する。`spec.json.freshness` が欠落している既存仕様は `unchecked` として対象範囲を調べ、欠落だけで承認を消去しない。`current` は文書整合のみを表し、承認・実装完了の代わりにならない。完了対象に `pending` が残る場合は影響を解決し、本文の意味も照合する。

## 着手と同期

1. 対象の `spec.json`、要件・設計・タスク、基本 steering と変更に関係する追加規則を読む。現在の内容を取得済みなら読み直さない。
2. [kiro-spec-sync](../kiro-spec-sync/SKILL.md) で現行仕様と変更根拠の整合性を確認する。古い要件・設計を追記だけで温存せず、同期の規則に従って本文と影響先を更新する。コードの不具合に合わせて受け入れ条件を緩めない。
3. 同期後の要件・設計・タスクの承認と実装準備状態を確認する。既存の明示的な承認を尊重し、同期で無効化された範囲の承認を推測しない。未承認部分の実装は保留し、調査・修正文書の作成や独立した承認済み作業を進める。
4. リポジトリの scripts / manifests、task runner、CI、統合テスト設定から必要なテスト・ビルド・smoke コマンドを特定する。仕様文書だけの修正にアプリ起動を要求しない。
5. 作業開始時の HEAD、`git status --porcelain`、`git diff`、`git diff --cached`、未追跡ファイルを記録し、既存変更を識別する。既存変更と重なるファイルは開始時の内容または差分を保持する。コミット後もこの開始点をレビューの基準として保持する。

## タスクの選択と実行

- 実行単位は番号の深さに依存しない。子を持たない具体的なタスクを実行し、子を持つ親は全対象の完了を集約する。
- `_Depends:_` を確認して前提から実行する。承認済み範囲での順序修正や分割・統合は自律的に行い、変更理由を記録する。意味や責務が変わる場合は同期による承認判定に戻る。
- `_Blocked:_` は今も有効か確認する。外部条件・権限・未承認の重要判断を待つ場合だけ維持し、通常のコード修正や調査の難しさを blocked に置き換えない。
- 小さく連続する変更は同じ文脈で処理する。独立した責務を並行実装できる場合はサブエージェントへ分担してよい。所有ファイル、依存契約、他者変更を戻さないことを明示する。
- 各実行単位で受け入れ条件、設計制約、責務境界、検証方法を具体化する。製品の振る舞いに影響しない通常判断は既存文脈から決める。
- バグ修正は可能な限り先に再現テストを実行し、機能変更は観測可能な受け入れ条件をテストする。RED を取得できない場合は理由と代替検証を示す。検証のためだけの一時 feature flag や非行動変更の失敗テストを要求しない。
- 実装、関連回帰検証、差分レビューを行う。新たな失敗は [kiro-debug](../kiro-debug/SKILL.md) で原因を絞る。同じ失敗には新しい根拠や仮説を用意し、無変更の再試行を重ねない。

## レビューと完了

- [kiro-review](../kiro-review/SKILL.md) を適用する。公開契約、認証・権限、データ移行、責務境界、複数コンポーネント連携の変更では、利用可能なら独立したレビュアーへ依頼する。低リスクの局所変更は自己レビューでよい。独立レビューを実施できない場合はその限界を報告する。
- レビュー指摘は実際の差分と仕様に照らして修正する。上流の不具合は所有箇所で直し、下流の回避策で隠さない。依頼範囲に含まれる通常修正は自律的に進め、範囲外の製品変更が必要なら具体案を示す。
- 完了前に `kiro-spec-sync` で実装で判明した変更の影響先を再確認する。仕様同期と承認、再オープンされたタスク、依存先の再検証を解決するまで該当範囲を完了扱いにしない。
- [kiro-verify-completion](../kiro-verify-completion/SKILL.md) で主張と証拠を照合してから `[x]` にする。同じ検証対象状態の証拠を再利用し、関連状態が変わった場合に再実行する。
- 全未完了タスクを対象にした場合は [kiro-validate-impl](../kiro-validate-impl/SKILL.md) で統合検証する。指定タスクのみの場合は検証・完了主張をその範囲に限定する。
- commit はユーザーの明示的な承認がある場合だけ行う。承認時も対象ファイルを選択して staging し、既存変更を混入させない。実装の依頼だけから commit / push の許可を推測しない。

## 分担時の入出力

実装には [implementer-prompt.md](templates/implementer-prompt.md)、レビューには [reviewer-prompt.md](templates/reviewer-prompt.md)、原因調査には [debugger-prompt.md](templates/debugger-prompt.md) を使う。テンプレートは入力と報告形式を定め、手順は各スキルを参照する。報告の欠落が判断に影響する場合だけ不足部分を確認し、見出しの表記差だけで再派遣しない。

結果は spec.json の言語で、完了・残作業、変更理由、検証結果と制限、同期した仕様、必要な承認を簡潔に報告する。

## 構造と確認対象の検査

[OKF の共通手順](../kiro-spec-sync/references/okf-workflow.md) の `check` を対象範囲へ実行する。機械検査の成功と意味の検査を区別し、古いハッシュや承認を現在の状態の証拠にしない。読取専用の依頼では snapshot、index、状態更新を実行しない。

完了チェック更新後は、本文にそれ以外の変更がないことを確かめ、共通手順で snapshot と check を最後に行う。直前の検証結果を再利用し、チェックボックスの更新だけでアプリの検証を繰り返さない。
