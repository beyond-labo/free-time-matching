# 仕様と知識の同期

既存の `.kiro` を現行の知識として維持する。
新しい Wiki ディレクトリや全文の複製は作らない。
[OKF の共通手順](references/okf-workflow.md) で文書形式、機械検査、確認対象の記録を扱う。
ユーザーの変更指示は望ましい振る舞いの根拠、コードと検証結果は実際の振る舞いの根拠として扱う。
実装の不具合を仕様変更で正当化しない。

## 入力と適用範囲

`$kiro-spec-sync [feature] [--check]`。
feature 未指定時は変更ファイルと依頼から対象を絞る。
全体棚卸しを依頼された場合だけ全仕様と steering を調べる。
呼出し元の工程へ結果を返し、仕様生成や実装を再帰的に呼び出さない。

`--check` または読取専用の依頼では、文書と状態を変更せず差異と必要な更新を報告する。
通常モードでは許可済みの変更に必要な本文修正と状態更新を同じ作業内で行う。
未採用の変更案を点検するときは、現行文書の整合状態と、案を採用した場合の更新対象を別々に報告する。案との差だけで現行文書を `NEEDS_SYNC` と判定しない。
依頼範囲外の製品判断が必要なら該当項目を保留し、独立した作業は進める。

## 変更の取り込み

1. 作業開始時の差分と既存変更を確認し、今回の変更を区別する。追跡済み、ステージ済み、未追跡のファイルを含める。
2. 変更の根拠を特定する。ユーザーの決定、該当コミットやファイル、再現結果、参照した一次資料のURLと確認日を必要な範囲で使う。日付の新しさだけで正しいと判定しない。
3. 要件ID、契約名、旧名称、変更ファイルのパスを `rg` で仕様、steering、関連文書から検索する。roadmap の依存先に加えて逆参照を確認し、影響先の参照もたどる。名前だけ一致する無関係な文書は除く。
4. 下表で分類する。意味変更が確定した時点で、下記の承認失効と `needs-sync` の記録を先に行い、下流の更新途中で中断しても古い承認が有効に見えないようにする。その後、現行本文を修正する。旧説明に追記するだけで矛盾を残さない。未知の製品判断は現行の確定事項と混ぜない。
5. 同じ根拠に依存する設計、タスク、テスト、brief、roadmap、ローカル方針を必要な範囲で更新する。根拠が足りない影響先は保留として記録する。並列作業の所有範囲を越える場合は自分で書き換えず、対象パスと更新理由を担当コントローラーへ返す。コントローラーが担当を調整して同期するまで未同期として扱う。
6. 根拠と意味上の変更理由を `research.md` の変更記録へ追記し、現行要約を更新する。仕様に属さない変更は該当文書の履歴または既存の決定記録へ短く残す。単なる表記修正に履歴の増設は不要。

| 変更 | 本文と状態への反映 |
|---|---|
| 誤字、整形、意味を維持したリンク修正 | 本文だけ更新。承認と完了を維持する。 |
| 要件の振る舞い、制約、受け入れ条件 | 要件と影響する設計、タスク、検証を更新。要件以降の承認を無効化する。 |
| 設計の契約、責務、依存関係 | 要件を満たすことを確認し、設計とタスクの承認を無効化する。要件も変わるなら上の扱い。 |
| タスクの成果や範囲の変更 | タスク承認を無効化。順序整理だけで成果と契約が不変なら根拠を記録して承認を維持できる。 |
| 既存要件を満たすバグ修正 | 要件の承認は維持。影響する完了タスクと検証を再評価し、修正結果と実装上の知見を反映する。 |
| upstream の契約や共通方針 | 影響する downstream の最初の変化する工程から承認を無効化。無関係な仕様の状態は維持する。 |

## 承認と完了の整合性

- 意味が変わった工程と下流の `approvals.<phase>.approved` を `false` にし、`ready_for_implementation` を `false` にする。`generated` は既存成果物の有無として保持する。
- `phase` は最後の生成工程を示し、承認や鮮度の証拠に使わない。工程の成果物を初めて生成した場合は `requirements-generated`、`design-generated`、`tasks-generated` の対応する値へ進める。再同期だけで既存値を巻き戻さず、未知フィールドを維持する。
- 影響した `[x]` タスクは、旧検証が新しい受け入れ条件を証明しない場合に `[ ]` に戻す。子を戻したら集約用の親も戻す。無関係な完了タスクは維持する。
- 番号の形式によらず末端タスクを実行単位とする。要件IDは安定させ、削除したIDを別の意味に再利用しない。IDを変える場合は旧新対応と参照更新を確認する。
- roadmap の `[x]` は仕様生成の完了であり実装完了ではない。影響で仕様生成が未完了になった項目を戻し、修復と点検後に再設定する。
- 既存の明示的許可（`-y`、`--auto`、自然言語の一括許可を含む）が改訂範囲をカバーするなら、改訂と品質確認後に該当承認を再設定できる。古い `approved: true` だけを新しい内容への許可と解釈しない。
- 同期と承認反映の最後に `ready_for_implementation` を必ず再計算する。全工程のファイルが存在し、`generated` と `approved` がすべて true で、`freshness.status` が `current`、`pending` が空の場合は true、それ以外は false にする。この値は実装完了や検証成功を意味しない。

## 同期状態

既存の `spec.json` には対象を更新するときに次のフィールドを追加できる。
テンプレートからの新規作成は `unchecked` とする。

```json
"freshness": {
  "status": "needs-sync",
  "pending": [
    {"path": ".kiro/specs/example/design.md", "reason": "変更した応答契約の反映待ち"}
  ]
}
```

- `unchecked`：まだ整合性を調べていない。旧仕様にフィールドがない場合もこれとして扱い、一律の承認削除や全件移行はしない。
- `needs-sync`：未反映や判断待ちがある。`pending` に対象パスと具体的な理由を記録し、実装可能フラグを下げる。
- `current`：対象の現存文書と影響先を確認し、未同期事項がない。`pending` は空にする。未生成の後続文書や未実装機能の完成を意味しない。

この状態は同期時点の記録であり、後続の変更の検出には共通手順の `check` と checked_inputs を使う。
ハッシュの不一致または確認記録の欠落がある場合、保存された current や ready だけでは実装開始と完了を認めない。意味を照合して必要な更新と確認記録を反映する。
実装前と完了前には差分と参照先を確認する。
未同期事項を記録してから作業を中断すれば、再開時に確認できる。

## 整合性点検と出力

更新した本文と影響先を読み直し、次を確認する。

- 旧契約や旧名称が現行の指示として残っていない。履歴に残すものは置換先と失効理由が明確である。
- 要件から設計、タスクへの対応、相互参照、責務、依存順が一致する。
- 承認、生成、同期、実装完了を混同していない。削除された要件の実装やテストを残すかも検討した。
- 証拠が変更後の状態と一致する。コード、依存関係、設定、環境、受け入れ条件に影響がなければ検証結果を再利用する。
- 未許可の製品判断や未実施の検証は残件として明示している。

通常モードでは意味の検査後に共通手順の snapshot で対象入力を記録し、上の判定を freshness と実装可能フラグへ反映する。check が対象の構造と入力一致を確認できることも実装可能の条件とする。読取専用では再計算の必要性を報告するだけにする。
結果は `CURRENT`、`NEEDS_SYNC`、`UNCHECKED` のいずれかと、対象、変更根拠、更新ファイル、無効化した承認や完了、残件を簡潔に返す。
読取専用では必要な変更を提案として返す。

## 設計の出典

[Karpathy の LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)（2026-09-06確認）の、情報を既存知識へ統合する運用、整合性点検、現行本文と変更履歴の分離を仕様駆動開発へ適用した。
承認の失効とタスク再開は、このリポジトリ用に加えた規則である。
